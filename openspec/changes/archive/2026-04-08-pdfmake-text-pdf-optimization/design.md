## Context

当前项目使用html2canvas + jsPDF方案生成简历PDF，这种方式通过截图生成图片型PDF。虽然实现了基本的PDF导出功能，但存在以下问题：
- 生成的PDF是图片格式，文字无法选中、复制、搜索
- 放大后文字边缘模糊，影响阅读体验
- 文件体积较大
- 不符合专业简历的标准

项目已经完成了基础架构搭建，包括Vue 3 + Element Plus的三栏布局、Pinia状态管理、以及基础的PDF导出功能。现在需要升级为专业的文本型PDF生成方案。

## Goals / Non-Goals

**Goals:**
- 实现真正的文本型PDF生成，支持文字选中、复制、搜索
- 保持与现有简历数据结构的兼容性
- 确保中文字体正确显示和渲染
- 提供专业的简历排版效果
- 支持A4页面尺寸和适当的页边距
- 实现自动分页和布局优化

**Non-Goals:**
- 完全重构现有的简历编辑界面
- 移除现有的html2canvas + jsPDF代码（保留作为fallback）
- 实现复杂的图形和图表支持
- 支持所有CSS样式的完美转换

## Decisions

### 1. 技术选型：pdfmake
**决策**：选择pdfmake作为新的PDF生成库
**理由**：
- 专为文本型PDF设计，完美匹配需求
- 良好的中文字体支持
- 声明式API，易于维护和扩展
- 活跃的社区和完善的文档
- 纯前端实现，无需服务端依赖

**替代方案对比**：
- **jsPDF原生API**：需要手动计算所有布局，开发复杂度高
- **Puppeteer**：需要服务端支持，过度设计
- **@react-pdf/renderer**：React生态，Vue项目集成成本高

### 2. 架构设计：分层架构
**决策**：采用数据层 -> 模板层 -> 生成层的分层架构

```
简历数据 (Pinia Store)
    ↓
PDF数据转换器
    ↓
简历模板定义 (pdfmake格式)
    ↓
PDF生成器 (pdfmake)
    ↓
文本型PDF文件
```

**理由**：
- 职责分离，便于维护
- 数据转换逻辑可复用
- 模板定义可配置化
- 生成逻辑独立，易于测试

### 3. 中文字体处理 - 已移除
**当前决策**：暂时移除中文字体支持，使用pdfmake默认字体

**实现方案**：
- 使用pdfmake内置的Roboto字体处理所有文本内容
- 移除所有中文字体相关的配置和加载逻辑
- 保持简洁的字体配置，专注于核心PDF生成功能

**移除原因**：
- 中文字体加载机制存在无法解决的兼容性问题
- 字体文件体积过大（约8.6MB），影响应用性能
- 简化当前版本，确保核心功能稳定可用

**后续计划**：
- 在v1.1版本中重新评估和实现中文字体支持
- 考虑使用更稳定的字体加载方案
- 提供字体选择的配置选项

**理由**：
- 确保中英文混合内容的正确显示
- 避免字体缺失导致的乱码问题
- 保持PDF的专业外观
- 思源黑体是开源字体，无版权风险
- 支持离线使用，提升用户体验

### 4. 数据结构设计
**决策**：定义专门的PDF简历数据格式

```typescript
interface PDFResumeData {
  personalInfo: {
    name: string
    contact: string[]
    summary?: string
  }
  sections: {
    education?: PDFSection[]
    experience?: PDFSection[]
    skills?: string[]
    projects?: PDFSection[]
  }
}
```

**理由**：
- 与pdfmake的文档结构对齐
- 简化模板定义复杂度
- 便于数据验证和处理

## 中文字体集成设计 - 已暂停

### 当前状态：已移除

由于技术实现中的兼容性问题和性能考虑，中文字体集成功能已从当前版本中移除。

### 移除的字体设计方案

**原计划使用思源黑体（Source Han Sans SC）的原因：**

1. **开源免费**：采用SIL Open Font License，无商业使用限制
2. **完整中文支持**：覆盖简体中文常用字符集（GB2312标准）
3. **多字重选择**：提供Light、Regular、Bold等多个字重，满足不同样式需求
4. **专业外观**：Adobe设计，字形规范，适合简历等专业文档
5. **跨平台兼容**：在各种PDF阅读器和操作系统上显示一致

**移除原因**：
- 字体加载机制存在无法解决的兼容性bug
- 字体文件体积过大（约8.6MB），显著影响应用性能
- 当前版本优先确保核心PDF生成功能的稳定性

## Risks / Trade-offs

### 1. 中文字体兼容性风险
**[Risk]** 不同系统和PDF阅读器对中文字体的支持程度不同
**Mitigation**：
- 测试主流PDF阅读器的兼容性
- 提供字体fallback机制
- 在文档中说明字体要求

### 2. 样式转换复杂性
**[Risk]** 现有的CSS样式无法完全转换为pdfmake样式
**Mitigation**：
- 重新设计PDF专用的样式系统
- 保持简洁专业的简历风格
- 提供样式配置选项

### 3. 性能影响
**[Risk]** pdfmake库体积较大，可能影响页面加载性能
**Mitigation**：
- 使用动态导入延迟加载pdfmake
- 优化字体文件体积
- 实现生成进度提示

### 4. 学习曲线
**[Risk]** 团队需要学习pdfmake的API和概念
**Mitigation**：
- 编写详细的使用文档
- 提供示例代码和模板
- 渐进式迁移，降低风险

### 5. 回滚策略
**[Risk]** 新方案可能存在问题，需要快速回滚
**Mitigation**：
- 保留原有的html2canvas + jsPDF代码
- 实现方案切换机制
- 提供兼容性测试工具
